# PeakCast — Weather Chatbot for Alpine Sports in Austria

**Course:** Project: AI Use Case (IU International University, MSc Artificial Intelligence)
**Author:** Markus Pointner (IU14161364)
**Phase:** 2 — Implementation

---

## 1. Project goal

PeakCast is a chatbot that answers short weather forecast questions for people doing
outdoor and alpine sports in Austria — hikers, climbers, ski tourers and paragliders.

A user asks in plain English, for example *"How windy is it on the Hochkönig tomorrow?"*,
and gets a **one or two sentence answer with exact values, units and a short outdoor hint**.

The bot covers:

| Topic | Status | Why it matters |
| --- | --- | --- |
| Temperature | mandatory | layering, hypothermia risk |
| Sky condition (sunny / cloudy) | mandatory | summit view, orientation |
| Wind speed and gusts | mandatory | decides whether a paraglider can launch |
| Rain and snowfall | optional | fresh snow matters for ski tours |

PeakCast informs — it does **not** replace official mountain weather or avalanche reports.

## 2. Technical approach

Everything is plain Python so that every component stays transparent and no cloud
account or license key is needed. Deliberately **not** used: hosted chatbot frameworks
(Rasa, Dialogflow) and LLM APIs.

```
Streamlit chat UI          (app.py)
      ↓
Dialogue manager          (keeps last place, limits conversation length)
      ↓
NLU   ├─ intent classifier   (scikit-learn: TF-IDF + logistic regression)
      └─ slot extraction     (place from GeoNames Austria, day words by rules)
      ↓
Weather service           (Open-Meteo API, offline JSON dataset as fallback)
      ↓
Response generator        (templates with values, units and outdoor hint)
```

## 4. Setup

Requires **Python 3.12** (3.10–3.12 all work).

Check which versions are installed with `py --list` on Windows or
`python3 --version` on Linux/macOS. On Windows, avoid the bare `python` command:
if Python was never installed from the Microsoft Store it resolves to a stub that
reports no version at all. The `py` launcher is reliable.

### Windows (PowerShell)

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements-dev.txt
```

### Linux / macOS

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements-dev.txt
```

There are two requirement files, and the split matters for deployment:

| File | Contents | When |
| --- | --- | --- |
| `requirements.txt` | only what `streamlit run app.py` needs | installed on the deploy host |
| `requirements-dev.txt` | the above **plus** pytest and matplotlib | for running the tests and the training/evaluation scripts |

`requirements-dev.txt` includes `requirements.txt`, so the command above
installs everything. If you only want to *run* the chatbot, `pip install -r
requirements.txt` is enough.

All versions are pinned exactly, so the environment can be rebuilt
identically - on your machine and on the deploy host.

### Start the chatbot

With the virtual environment activated, from the project root:

```bash
streamlit run app.py
```

Streamlit prints a local URL (`http://localhost:8501`) and opens it in your
browser. If it does not open by itself, paste the URL in.

**What to expect on the first start.** The trained model is not part of the
repository - it is a build artefact that `models/` is git-ignored for - so the
app trains it the first time it runs. You will see
*"First start: training the intent classifier"* for about a second, then the
chat. Nothing has to be run by hand beforehand: no training script, no data
download. The place list (`data/places_at.csv`) and the offline demo forecasts
are committed.

**The chat.** Before the first question, three example questions are offered
as small chips above the input; tap one to send it, or type your own. The chips
disappear once the conversation has started. Follow-ups work without repeating yourself - ask
*"How windy is it on the Großglockner tomorrow?"*, then just *"And tomorrow?"*
or *"What about Kaprun?"*. Every answer is labelled with where its numbers came
from: **live forecast** or **sample data**. A conversation ends after ten
answers or when you say goodbye, and then offers a restart button.

**The sidebar** (the `»` arrow at the top left, or swipe in on a phone) holds a
short description, the safety disclaimer, the data attribution and two
switches:

| Switch | What it does |
| --- | --- |
| **Offline demo mode** | Answers from the built-in sample dataset instead of calling the weather API. Use it if the network fails during a presentation - answers stay clearly marked as sample data. |
| **Show NLU details** | Shows the recognised intent, its confidence and the extracted place and day under each answer. Off by default; useful for seeing *why* the bot answered as it did. |

### If something goes wrong

| Symptom | Cause and fix |
| --- | --- |
| `streamlit: command not found` | The virtual environment is not active. Re-run the activate line from the setup block above. |
| `Activate.ps1 cannot be loaded because running scripts is disabled` (Windows) | PowerShell's execution policy. Either run `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` first (it lasts only for that window), or skip activation and call the interpreter directly: `.\.venv\Scripts\python.exe -m streamlit run app.py`. |
| `python` reports no version (Windows) | That is the Microsoft Store stub. Use `py -3.12` instead, as in the setup block. |
| Every answer says **sample data** | No internet connection, or Open-Meteo is unreachable. The bot falls back to its demo dataset on purpose so it still works; the numbers are fictional. |
| The first start seems to hang | It is training the intent classifier. It takes about a second on a normal machine. |

### Running the intent classifier

Run in this order from the project root:

```bash
python scripts/train_intent.py                     # baseline: 5-fold CV, saves the model
python scripts/evaluate_intent.py                  # baseline test metrics -> reports/
python scripts/optimize_intent.py                  # iteration 1: grid search + threshold
python scripts/evaluate_intent.py --variant iter1  # iteration 1 test metrics -> reports/
python scripts/compare_iterations.py               # before/after chart + spot-checks
python scripts/try_intent.py                       # interactive: type a sentence
```

| Model | CV accuracy (train) | Test accuracy | Macro F1 |
| --- | --- | --- | --- |
| Baseline — word TF-IDF + logistic regression | 0.678 | 0.775 | 0.778 |
| **Iteration 1** — word + character n-grams, grid-searched | **0.803** | **0.813** | **0.812** |

All metrics, confusion matrices, the grid search table and every misclassified
sentence are written to `reports/`.

### Running the slot extraction (step 5)

```bash
python scripts/build_places.py        # download GeoNames, write data/places_at.csv
python scripts/evaluate_slots.py      # slot metrics -> reports/
```

`scripts/build_places.py` only needs to be run to rebuild or refresh the place
list - `data/places_at.csv` is committed, so the bot works straight from the
submitted files.

| Slot | Accuracy on `data/slots_test.csv` (52 sentences) |
| --- | --- |
| Place | **1.000** (52/52) |
| Day | **1.000** (52/52) |
| Part of day | **1.000** |

Measured against a fixed reference date (Wednesday 2026-11-04) so that relative
day words like *"on Friday"* stay reproducible. See `reports/metrics_slots.json`
and `reports/slot_extraction_check.csv`.

### Running the weather service (step 6)

```bash
python scripts/try_weather.py              # live, with offline fallback
python scripts/try_weather.py --offline    # force the fictional demo dataset
```

`try_weather.py` runs the whole chain for one typed message - safety guard,
place and day extraction, then the forecast - so a single screen shows every
component built so far.

Sky categories are derived from the WMO weather code and the mean cloud cover,
in this order: WMO 45/48 is `foggy`; any code from 51 (drizzle) upwards is
`cloudy`, so the bot never calls a raining hour sunny; otherwise cloud cover
decides, under 25 % `sunny`, 25-75 % `partly cloudy`, 75 % and above `cloudy`.

The place's **elevation** is sent with every request. Without it Open-Meteo
answers for the mean elevation of its grid cell, which near a summit is
noticeably different:

| Request for the Großglockner | Model elevation | Max temperature |
| --- | --- | --- |
| without the elevation parameter | 3 650 m | -8.9 °C |
| with `elevation=3798` | 3 798 m | -9.8 °C |

### Running the tests

Needs `requirements-dev.txt` installed (the setup block above does that):

```bash
python -m pytest           # 325 tests, no network needed
python -m pytest --live    # also runs three tests against the real API
```

The live tests are skipped by default: a suite that needs the internet fails on
a train or in a CI container. They are kept because a fully mocked suite can
pass while the real API has renamed a field.

### Talking to the bot (step 7)

```bash
python scripts/chat_cli.py                 # live forecasts
python scripts/chat_cli.py --offline       # fictional demo data only
python scripts/chat_cli.py --debug         # show intent, slots and source
python scripts/chat_cli.py --seed 17       # fixed phrasing, for a screenshot
```

On a fresh checkout there is no trained model (`models/*.joblib` is
git-ignored, being a build artefact), so the bot trains one on first start and
says so. Nothing else has to be run by hand.

A conversation, exactly as produced by `chat_cli.py --seed 17`:

```
You: How windy is it on the Hochkoenig today?

PeakCast: Today on the Hochkönig expect 27 km/h of wind and gusts to 61
          km/h. That is not flying weather, and exposed ridges will be
          unpleasant.

You: And tomorrow?

PeakCast: Wind on the Hochkönig tomorrow is around 16 km/h, with gusts up to
          35 km/h. Worth checking before you launch.

You: What about Kaprun?

PeakCast: Wind in Kaprun tomorrow is around 3 km/h, with gusts up to 4 km/h.
          Fog is likely, so do not count on the view or on landmarks.
```

Neither follow-up contains a weather word, so the intent classifier cannot
carry them on its own - *"And tomorrow?"* comes back at p = 0.31 and
*"What about Kaprun?"* as confident `out_of_scope`. The dialogue manager
reuses the remembered intent with the new slot instead. See `DEVLOG.md`,
step 7.

### The user interface (step 8)

```bash
streamlit run app.py
```

`app.py` is deliberately thin: it owns the screen and nothing else. Every
reply comes from `peakcast.dialogue.Bot.respond`, the same code path the
terminal client and the tests use, so there is no second bot behind the UI
that the tests do not cover.

The layout is centred and single-column because the target group is on a
phone: someone at a trailhead is not holding a laptop. Nothing essential lives
only in the sidebar, which collapses on a narrow screen.

Startup, chat behaviour, the two sidebar switches and the troubleshooting table
are described in [section 4](#4-setup).

### User tests (step 9)

Two things in the sidebar support a user test, and neither stores anything on
a server - there is no database, no log file and no analytics endpoint in this
project:

- a **thumbs up / down** control under each answer, optional and unlabelled;
- a **Download conversation** button, which writes the transcript as a `.txt`
  file in the participant's browser. They send it on themselves, which means
  they can read, edit or discard it first.

The file is plain text so a participant is actually able to check it before
sending. Under each answer it records what the bot recognised:

```
[2] 14:21:03 PEAKCAST
Wind on the Hochkönig tomorrow is around 16 km/h, with gusts up to 35 km/h.
    intent: ask_wind
    confidence: 0.92
    place: Hochkönig, Salzburg
    day: 2026-11-11
    source: live
    feedback: up
```

Collect the files in `data/user_tests/` (git-ignored - they are other people's
conversations) and summarise them:

```bash
python scripts/analyze_transcripts.py
python scripts/analyze_transcripts.py --json reports/user_tests.json
```

The summary reports per-intent counts, the forecast sources, the thumbs, and -
deliberately - the unflattering figures: turns below the confidence threshold,
ask-backs, "I didn't catch that" fallbacks, refusals, and every thumbs-down
with the question that produced it. Those are the rows that say what to fix
next.

## 6. Deployment (Streamlit Community Cloud)

The app runs unchanged on [Streamlit Community
Cloud](https://share.streamlit.io). Nothing about the local ZIP/README route
above changes - the same `app.py` and the same `requirements.txt`.

### What to click

**On GitHub**

1. Create a repository (private is fine) and push this project to it.
2. Make sure `app.py`, `requirements.txt`, `data/places_at.csv` and
   `data/offline_forecasts.json` are committed. They are - but it is worth
   checking after a fresh clone, because the app cannot work without them and
   `models/` is intentionally **not** committed.

**On Streamlit Community Cloud**

3. Go to [share.streamlit.io](https://share.streamlit.io) and sign in with
   GitHub.
4. Authorise the GitHub app. For a **private** repository you have to grant
   access to private repositories as well - if your repo does not appear in
   the list at the next step, this is why. The permission can be added later
   under *Settings → Linked accounts*.
5. Click **Create app** → deploy from an existing repository.
6. Fill in:
   - **Repository:** your repo
   - **Branch:** `master` (or `main`)
   - **Main file path:** `app.py`
7. Open **Advanced settings** and set **Python version** to **3.12**. This
   matters: the versions in `requirements.txt` are pinned, and a newer Python
   may not have matching wheels for them, which turns into a build failure.
   Leave **Secrets** empty - the app needs no API keys.
8. Click **Deploy**. The first build installs the dependencies and takes a few
   minutes.

### What to expect

| | |
| --- | --- |
| **First visit after a build** | The intent model is not in the repository, so the app trains it on the first page load and shows a spinner for about a second. The filesystem on the host is temporary, so this happens again after every cold start. |
| **Sleeping** | A free app goes to sleep after roughly **12 hours** without traffic. The next visitor sees a "wake up" screen; it takes about a **minute** to come back, plus the model training. Worth knowing before a presentation - open the app a few minutes beforehand. |
| **No network to Open-Meteo** | The app falls back to its built-in sample dataset and labels every answer `▲ sample data - not a real forecast`. It does not error. |
| **Memory** | The free tier gives about 1 GB per app. PeakCast loads scikit-learn plus a 2.2 MB place list, well inside that. |
| **Who can see it** | Anyone with the URL, even from a private repository - the repo is private, the app is not. Don't put anything confidential in it. |

> **Licence note:** the free Open-Meteo API is for **non-commercial use**
> ([terms](https://open-meteo.com/en/terms)). A publicly reachable deployment
> of this coursework project stays within that; a commercial deployment would
> need an Open-Meteo subscription, and only the endpoint URL in
> `peakcast/weather.py` would have to change.

> **Safety note:** the intent classifier labels *"avalanche risk after the fresh
> snow"* as a precipitation question with high confidence (p = 0.62, well above
> the 0.35 fallback threshold), and the better model is the more confidently
> wrong one. Avalanche questions are therefore intercepted by a rule-based guard
> in `peakcast/safety_guard.py` that runs **before** the classifier and returns a
> fixed referral, never a forecast. The referral points at
> [lawinen.at](https://lawinen.at), the joint portal of the Austrian state
> avalanche warning services, and adds
> [avalanche.report](https://avalanche.report) only for places in Tyrol, which
> is the extent of that bulletin's coverage. See `DEVLOG.md`, steps 2, 4, 5
> and 6.
